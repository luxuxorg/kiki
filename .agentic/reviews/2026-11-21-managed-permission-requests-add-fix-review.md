## Notes (non-blocking)

1. **Last-grant removal after a kiki add is refused (removal × mirror interaction).** With a kiki-written state `[grant, suffix]`, removing the only surviving grant leaves the orphaned suffix as positional inherited tuples → `protectProjectSurvivors` fails 'Legacy baseline mirror' (derivingAllows empty → trailingStart = length, permission-requests.ts:151-163,181-183); the suffix entries themselves are un-removable ('belongs to inherited/global', :312-314). Net: the CLI cannot fully unwind its own add; the escape is a manual file edit (spec-accepted outside the guarantee). This is the plan-conformant intersection of "do not drop obsolete-looking masks" (plan Task 3) and "fail closed on mirrors", in the safe direction, but it is untested (only the suffix-less final-grant case is covered, test:235-239) and user-visible. Final whole-task review should surface and document it (or refine recognition for the no-allow case).
2. **Inherited-ask positional acceptance asymmetry (pre-existing, untouched by the fix).** Inherited ASK tuples pass anywhere (`continue`, :174-175), unlike inherited denies (positional, :181-183) and allows (anywhere, :168-171). Only hand edits can produce such entries (managed writes cannot), so this is a `check`-detection gap rather than a managed-write weakness: a hand-copied `ask shell git push*` (config.ts:193) in a project tier would, under merged last-match, flip the inherited force-push denies (config.ts:217-223,269) to ask, and `kiki permissions check` would report no conflict. The handoff's blanket claim "positional inherited tuples still fail closed" is imprecise for asks. Final review should decide: tighten (treat positional inherited asks like denies) or document as accepted residual risk (spec §7).
