## Notes (non-blocking; to be addressed in the plan or a spec revision)

1. **§6.4 invariant 4 states the wrong justification for a correct conclusion.** "Both copies hold identical policy" is false during the real migration (the unstripped markdown still holds the stale 21-rule core; the config holds fresh). The window is nonetheless safe for a verifiable reason: every role's fresh array opens with broad anchors (`read *`, `edit *`, `shell *`) appended **after** all markdown rules, so for every request those actions the last matching rule lies inside the fresh array — the window's effective policy equals the new baseline exactly, and the stale markdown rules are dead weight. Reword the invariant to this mechanism and pin it as an explicit crash-window evaluation test (markdown-unstripped fixture → fresh decision).
2. **Idempotence (invariant 1) silently requires custom-rule dedup.** A re-run sees the same custom rules in *both* the unstripped markdown and the already-written config array; without exact-string dedup and a stable tail order, run 2 duplicates them and breaks byte-stability. State the dedup requirement and cover it in the §9.5 idempotence tests.
3. **§6.3's "catalog gaps are safe … worst case a duplicate append, never a loss" is wrong for uncataloged *denies*.** A preserved custom deny is appended after the fresh baseline and, by last-match, beats it — that is not a harmless duplicate. For this rollout the exposure is closed (§3.1 enumerates every live markdown rule set, and each is catalog-legacy or fresh-baseline; Gate 3's matrix would catch representative breakage), but the safety claim should be corrected, and the report strengthened: list replaced and preserved rules **verbatim** (not just counts), so a coincidental catalog collision (a user custom identical to a legacy signature gets dropped) is auditable, and treat any preserved deny found during the live transaction as halt-and-review rather than proceed. Related forward gap: when a future baseline *retires* a rule, the retired rule is neither fresh nor in the historical catalog, so it classifies as custom and persists (fail-safe for retired denies, drift for retired allows) — fold retired-rule handling into the D2 answer (per-release catalog extension or explicit report-and-approve).
4. **Prefer tracked git state over /tmp backups as verification canon.** `opencode.jsonc` is tracked; HEAD already contains the pre-round state (verified: 3 model blocks), so §8.2's "verify from the 08:24 backup" and D1's restoration source should name `git show HEAD:opencode.jsonc` first — /tmp is ephemeral and may be gone at rollout time. The §6.3 catalog itself is fine: it is pinned in code/tests; the /tmp artifacts are provenance only.
5. **Gate 3 has an unstated environment prerequisite.** The isolated harness requires `OPENCODE_TEST_BINARY`; the prior round's own evidence shows it is currently absent on this machine (4 broad-suite failures attributed to it). The plan must record supplying the binary as a Gate-3 precondition, otherwise the mandatory precedence validation cannot run.

## Conclusion

The spec faithfully implements the fixed architecture, matches the user-approved retained policy exactly, accurately reports the verified current state, keeps code implementation, planned cleanup, and live rollout behind separate approval gates, mandates no changes now (and none were made), and its two new abstractions are justified and bounded. No major blocker with complete evidence was found.
