### Ursprünglich dokumentierter Zweck

- **Single-Source (2026-11-19):** „Kiki's role permissions currently live in several drifting copies — generator templates, global agent markdowns, and project-config mirrors … Goal: one baseline location, refreshed by `kiki update`, with project configs holding additive file/folder permissions and independent model settings" (Spec :9-15). Fixe Architektur: globale Konfiguration owns die vollen Rollen-Arrays unter `agents.<name>.permissions` („a kiki-maintained field", :21-24); Projekt = nur additive Datei-/Ordner-Rechte (:27-30).
- **Managed Permission Requests (2026-11-20):** drei Lücken nach bb1acee — **(a)** „`kiki update` recognizes its own past output only by content-shape catalog — manual divergence is silently preserved as 'customs' or halts as ambiguous"; **(b)** Projekt-Permission-Änderungen sind „raw hand-edits — unvalidated, unbacked, bypassable"; **(c)** die neuen Command-Rules mussten am echten Binary gemessen werden. Nutzer-Ziel (KISS): „clean, convergent `kiki update`, no persistent garbage" (Spec :7-15).
- **Zweck des Hash (§3A, Spec :33-35):** „Versioned per-role hashes of the exact `agents.<name>.permissions` field kiki last wrote — evidence only, no rules stored, never a second policy source. On update: preflight re-hash; unmodified owned field → replace with fresh baseline + rewrite hash; mismatch (manual divergence) → halt with a per-role drift report … never overwrite; absent/stale/corrupt state → conservative legacy bootstrap via the existing content classifier." Einzigartiger Wert: der Klassifikator allein „cannot distinguish kiki's older outputs from user edits — they halt as 'ambiguous' and owned-field drift is silently preserved as customs; the state record removes both failure modes."

### Antwort auf die Kausalitätsfrage

**Der Hash/drift wurde NICHT durch die Projekt-Permissions eingeführt und war auch nicht früher da — er kam im selben Commit (`8c71efe`) und selben Spec wie das Projekt-CLI, ist aber ein eigenständiger Mechanismus für den globalen Update-Pfad** (Lücke (a)), nicht eine Folge der Projekt-Rechte (Lücke (b)). Code-Beweis: `permission-requests.ts` und `commands/permissions.ts` importieren keine Ownership-Funktionen; `state.json` wird ausschließlich von `installGlobalFiles` (install/update) geschrieben (`opencode-config.ts:781-782, 964-966`). `kiki permissions add` erzeugt also **keinen** Drift und berührt **keinen** Hash. Die Projekt-Permissions-Freigabe des Nutzers ist zugleich die Freigabe des Specs, der den Hash enthält — beides wurde gemeinsam approbiert (Registry :37; Spec-Status :3-5).

## B. Frage 2 — Ownership & Hash-Granularität

**Was wird verwaltet/gehasht:**

- Verwaltet („kiki-maintained"): ausschließlich die 8 Felder `agents.<name>.permissions` der Kiki-Rollen (`AGENT_NAMES`, `opencode-config.ts:29-30`) in der **globalen Ziel-Datei**. Ziel = letzte existierende Kandidatin aus `['opencode.json','opencode.jsonc']`, d. h. `opencode.jsonc`, wenn beide existieren (`configTarget`, :231-233). Globaler Root: `OPENCODE_CONFIG_DIR` oder `$XDG_CONFIG_HOME/opencode` oder `~/.config/opencode` (`oc2-paths.ts:23`; README:110).
- Hash-Granularität: **pro Rolle**, SHA-256 über `JSON.stringify(rules)` des geparsten Arrays (`permission-ownership.ts:20-22`). „Array order matters and JSONC whitespace does not" (:8-11). **Kanalisierung:** Whitespace/Kommentare/trailing commas sind irrelevant (Parse über `readSettings`, `opencode-config.ts:164-168`); **Elementreihenfolge** und — because `JSON.stringify` insertionsordnungs-sensitiv — **auch die Schlüsselreihenfolge innerhalb jedes Rule-Objekts** gehen in den Hash ein. Ein handgetipptes, semantisch identisches `{"resource":…,"action":…,"effect":…}` erzeugt daher Drift.
- State-Datei: `<global>/kiki/state.json`, Format exakt `{version:1, roles:{<role>:<64-hex>}}`, strikt validiert — jede Abweichung (unbekannte Version, Extra-Feld, Non-Hash, `__proto__` etc.) → `undefined` → Klassifikator-Bootstrap (`permission-ownership.ts:28-46, 53-61`). Serialization deterministisch, atomar geschrieben, Verzeichnis mode 0700, Datei 0600 (`:64-71`; `opencode-config.ts:964-966`, `writeAtomic` :235-244).

**Löst ein beliebiger manueller Edit der globalen `opencode.json(c)` den Stopp aus?** Nein — nur drei Drift-Ursachen plus generische Validierungsstopps:

1. **Managed Subset verändert:** Feld fehlt („owned permission field is missing", `opencode-config.ts:796-798`), Hash-Mismatch (:800-802), oder es existiert eine **konkurrierende Permission-Quelle** — ein anderes globales Config-File mit Kiki-Rollen-Permissions oder Permissions im Agent-Markdown-Frontmatter (:804-809; Quellensammlung in `collectAgentSources` :681-725). Alles → „Refusing to update permissions; manual resolution required" mit Drift-Report (:748-762, :843-847).
2. **Validierungsstopps (kein Drift, aber auch Halt):** unparsebare/ungültige Konfiguration, `__proto__`-artige Schlüssel, ungültige Permission-Shapes in **beliebigem** Agent (`readSettings` :164-185), doppelte Agent-Schlüssel (:766-776; Duplikate außerhalb der `agents`-Map sind explizit irrelevant, :626-631), Kommentare innerhalb eines zu ersetzenden Permission-Arrays (:889-902), Konflikt/Duplikat des Managed-Fragments im Prompt (`config.ts:570-577`).
3. **Unverwandte, valide Edits — kein Stopp, keine Schreibberührung:** Modelle, top-level `permissions`/andere Keys, Kommentare außerhalb der Arrays, Nicht-Kiki-Agents. `patchAgents` schreibt nur `agents.<name>`-Pfade JSONC-erhaltend (:246-267); `patchValue` ist bei Gleichheit ein No-op (:249); README:103-104 „Models, comments, unrelated settings … are preserved". (Vereinzelter Rest: Feldinhalte von Nicht-Kiki-Agents werden von `patchAgents` nicht angefasst, wohl aber von `removeAgentPermissions` nur für Kiki-Rollen-Namen, :941-943.)

## C. Frage 3 — `kiki update`-Verhalten (Tabelle)

`kiki update` = **ein einziger Aufruf** `installGlobalFiles(undefined, true)` (`update.ts:4-7`); „projects are untouched" (:6). Es gibt **keinen separaten Permission-Update-Scope** — Permission-Refresh, Markdown-Refresh, Workflow-Datei und Registration laufen in einer Transaktion; ein Drift-Halt stoppt also das **gesamte** globale Update.

| Szenario | Verhalten (Code) |
|---|---|
| Baseline unangetastet (Hash matcht, keine Fremdquelle, keine Blocker) | Ersetze Feld mit frischem Baseline (prefix + erhaltene customs + Secret-Tail, :814-827, :826-827), Hash neu schreiben (:904-909, :964-969). Völliger No-op (auch State unverändert) → Early-Return ohne Schreiben (:911-915). Fehlender State bei sonst gleicher Baseline → nur `state.json` wird ergänzt (`stateNeedsChange` :908-909; Final Review:29) |
| Manuell geänderte **verwaltete** Felder (State vorhanden) | Drift über **alle** Rollen sammeln, dann ein Halt **vor jedem Schreiben und vor dem Backup** (:788-847 vs. Backup :926 — „no writes, no backups", Final Review:17; CHANGELOG:62-63). Report: recorded/current Hash, „rule diff: unavailable (hash-only evidence stores no rules)" (:748-762). **Kein Überschreiben**; jeder Rerun stoppt weiter, bis aufgelöst |
| Manuelles Edit **ohne** State (Bootstrap-Fall) | Klassifikator-Pfad: erkannte generierte Shapes werden ersetzt; unbekannte Allow-Regeln bleiben als customs erhalten; **custom deny / unvollständige generierte Form / konflikthafte Effekte → Halt** (:831-841; `permission-consolidation.ts:4147-4156, 4165-4183`; README:114-115) |
| Unverwandte globale Edits | Kein Hash-Einfluss → Update läuft; Felder bleiben unberührt (siehe B.3) |
| Projekt-/inherited-Zusätze | Werden von `update` **nie traversiert oder geschrieben** (Spec 2026-11-20:35 „Project configs are never traversed or rewritten by update; handwritten project additions are user-owned immutable data"; `installGlobalFiles` operiert nur auf dem globalen Verzeichnis). Kein Einfluss auf Hashes |
| Backup & Overwrite bei laufender Transaktion | Backup aller berührten Dateien nach `<global>/kiki/backups/<uuid>/` (0700/0600, manifest.json, `.gitignore '*'`, :454-464, :917-926). Alte Evidenz wird **vor** der ersten Permission-Mutation invalidiert (:930-934); Reihenfolge registration → `patchAgents` → Re-Read-Verify → Markdown-Strip → Verify → State-Veröffentlichung **erst nach** Config-Verifikation (:939-969); Rollback stellt Config zuerst, State zuletzt wieder; bei unvollständigem Rollback bleibt Evidenz **absent** (:970-998). Kein atomarer Multi-File-Claim (README:118-121) |
| Race: manueller Edit **während** des Updates | Kein exaktes Byte-Precondition auf dem globalen Pfad — wird überschrieben, Post-Write-Verify fängt Konsistenz ab (Final Review Note 4; README:123-124). Nicht neu in 8c71efe, kein Regressionsclaim |

**Unterstützte Auflösungs-/Override-Routen (nur verifizierte):**

- **Kein Override-Flag existiert.** `--force` ist bei `update`/`install` wirkungslos toleriert (`args.ts:41` — wird stillschweigend übersprungen; README:106 „`kiki install --force` does not bypass these checks"); ein echtes `--force` gibt es nur bei `kiki migrate` (V1-Migration, `args.ts:9-32`).
- Dokumentierte Wege: (1) den manuellen Edit **rückgängig machen**, sodass das Feld wieder exakt dem recorded Hash entspricht; (2) `kiki/state.json` entfernen/ungültig machen → Legacy-Classifier-Bootstrap (customs bleiben, custom deny/ambiguous halten) — Verhalten dokumentiert README:114-115, Spec 2026-11-20:35 („deleting the file restores today's behavior"). **Nicht dokumentiert** als Nutzerworkflow, aber technisch die einzige Route, wie ein manuelles globales Allow dauerhaft in die verwaltete Baseline übernommen wird (Bootstrap bewahrt customs, neuer Hash deckt dann prefix+customs+tail ab, :840-841 + :906).
- Permanent-sanktionierte globale Änderung: Generator-Änderung im Kiki-Repo + `kiki update` (Spec 2026-11-20:51-52; Details §E).

## D. Frage 4 — Projektpfade (`kiki permissions`) & Interaktion mit globalen Hashes

- **list/check:** genuin read-only, Metadaten-only (`permission-requests.ts:67-82` „Inspect metadata only: no provider/model/prompt settings ever leave this function"; README:251-256; zero-write per FS-Instrumentierungstest, Final Review:19). `check` meldet Konflikte (doppelte Agent-Keys, Legacy-Baseline-Mirror, unsichere surviving asks) und exit != 0 (`commands/permissions.ts:162-184`; `protectProjectSurvivors` `permission-requests.ts:143-196`).
- **add:** genau ein enge Literal-Grant, nur `allow` + `read|edit` (`commands/permissions.ts:34, 122-127, 192-194`; `planPermissionAdd` `permission-requests.ts:274-300`: Non-allow/Non-read-edit verweigert :279-282, redundante/covered Grants verweigert :289-291, Ineffektivitäts-Probe :292-298). Validator (unverändert, `oc2-permissions.ts:103-144`) lehnt Secrets/Grenzen/Publishing ab und hängt protective masks + Secret-Suffix an.
- **remove:** löscht exakt den selektierten Index+Tupel — inklusive handschriftlicher Einträge; verweigert inherited/global entries (:312-313) und Einträge, die als Mandatory-Protection noch gebraucht werden (:318-320); rechnet Schutz für Survivors neu.
- **Ziel-Scope:** ausschließlich Projektkonfiguration (`PROJECT_CONFIG_NAMES` `permission-requests.ts:31-36`; `selectProjectTarget` :104-134 und `assertProjectFile` :324-331 verweigern alles außerhalb der Projektkandidaten und jede Überlappung mit dem globalen Root; Symlink-auf-Global wird vor jedem Schreiben verweigert, Final Review:23). „The CLI edits only project configuration; global policy and markdown are never changed" (`commands/permissions.ts:38`; README:251).
- **Interaktion mit globalen Hashes: keine.** Weder `add`/`remove`/`list`/`check` schreiben `state.json` oder die globale Konfiguration (keine Ownership-Imports in `permission-requests.ts`/`commands/permissions.ts`; State-Writer existiert nur in `opencode-config.ts`). Indirekte Kopplung existiert nur lesend: `inheritedPermissionRules` liest die globale Baseline zur Planungszeit (:84-94; :191, :215). Zwei Design-Kopplungen ohne Automatik: (a) ändert sich später die globale Baseline, kann ein alter Projekt-Grant redundant/overshadowed werden — sichtbar erst über `check`/nächste add/remove (fail-closed, kein Auto-Sync); (b) `kiki permissions` bricht mit sanitisiertem Fehler ab, wenn die globale Konfiguration unparsebar ist („Invalid OpenCode configuration: <file>", `readSettings` :168; Final Review:19).
- Transaktion: Backup nach `<project>/.agentic/kiki/backups` (:389), Byte-Precheck + Re-Check unmittelbar vor Schreiben (:369-372, :392-395), Verify + Rollback nur des eigenen Postimages (:398-429) — TOCTOU-Disziplin, die der globale Pfad bewusst nicht hat (Final Review Note 4).

## E. Frage 5 — Gap/Tradeoff: Low-Friction-Overrides vs. Single-Source-Intention

**Dokumentierter, approbierter Scope (Belege):**

- Single-Source-Ziel inkl. „additions only" fürs Projekt, Global owns die Arrays (Spec 2026-11-19:21-31); Nutzer-Entscheidung „Kiki-managed writes only … Arbitrary manual edits outside Kiki are not policed; native last-match overrides remain possible and this residual risk is accepted" (:128-130); Batch-Rollout approbiert (:3-4, :165-171).
- 2026-11-20-Spec approbiert (Registry :37 „spec freigegeben von mir. Aber nicht dispatchen!"; Spec :3-5), inkl. Drift-Halt (§3A:35, Akzeptanz §6:2) und Remove-Klärung „Ja, Schutz bleibt" (:5, :63).
- Hash-Drift ist damit **dokumentiertes, approbiertes Verhalten** — README widmet ihm einen eigenen Absatz (:108-124) mit dem ausdrücklichen Satz: „The hash does not detect or prevent arbitrary manual edits — it makes divergence on an owned field visible to the next update." (:116-117).

**Der eigentliche Tradeoff:**

- **Low friction auf Projektebene** existiert und ist die approbierte Lösung für den Anwendungsfall „Agent braucht zusätzliche Datei-/Ordnerrechte": `kiki permissions add … --apply` hinter nativem Ask (Spec §3B; Command-Rules: `list/check` = allow, `add/remove` = ask, unmittelbar nach dem `shell *`-Allow für alle 8 Rollen, `config.ts:231-256, 258-271`; am echten Binary 160/160 identisch gemessen, Spec 2026-11-20:73-77).
- **Global gibt es bewusst KEINE low-friction-Route:** „The CLI never edits global policy, prompts, or markdown. New global ASK shell patterns — including the generator ask patterns — flow only through the reviewed Kiki generator + `kiki update`, never through this command" (Spec 2026-11-20:50-52; README:251; `commands/permissions.ts:38`). Sanktioniert = Generator-Code im Kiki-Repo ändern + normaler Update-Lauf. Alles andere ist manueller Edit: **wirkt sofort zur Laufzeit** (native last-match-Präzedenz, README:244-245; kein Runtime-Policing, 2026-11-19:128-130), **friert aber künftige `kiki update`-Läufe ein**, bis er revertiert oder `state.json` geopfert wird (§C).
- Abgrenzung Annahme vs. Beleg: Die Freigabe-Belege decken die beiden Specs samt dieses Verhaltens ab. **Nicht belegt** ist, dass der Nutzer die konkrete Friktion („schnelle dauerhafte globale Anpassung ohne Codeänderung") jemals als eigenständiges Designziel diskutiert oder entschieden hätte — ein `kiki permissions add --global` existiert nirgends und sein Fehlen ist Design (§3B), aber die praktische Konsequenz ist emergent. Für diese Lücke gibt es keinen verifizierten Feature-Route-Claim.

## G. Limitationen, Docs-vs-Code, Code vs. Live-State

- **Installierter/live Zustand unbekannt:** Ob `~/.config/opencode/kiki/state.json` existiert, ob je manuell global editiert wurde, und welche CLI-Version live läuft, wurde — dem Auftrag folgend — **nicht inspiziert**. Die Features stehen unter CHANGELOG `[Unreleased]` (Version 3.1.1, `config.ts:96`, `package.json`); `dist/cli/permission-ownership.js` ist in `8c71efe` committet (`git show 8c71efe:dist/cli/permission-ownership.js` — Hash-Import sichtbar), aber ob die globale Installation diesen Stand fährt, ist Live-State. Alle Aussagen hier sind **Code-Verhaltens**-Aussagen.
- **Docs-vs-Code:** README 100-124 (Update/State/Drift/Bootstrap), 240-247 (Baseline-Präzedenz, kein Hook), 249-303 (CLI-Scope, TOCTOU, Remove, Ask-Semantik) und CHANGELOG 42-79 wurden punktgenau gegen den Code verifiziert — **konsistent**. Eine Unschärfe gefunden: Spec 2026-11-20:35 „conflicts are reported at project check/init/migrate" — Konflikt-Erkennung (Mirror/unsafe ask) existiert nur in `kiki permissions check` (`protectProjectSurvivors` nur dort verwendet, grep über `src/`: 9 Treffer, alle in `permission-requests.ts`/`commands/permissions.ts`); `kiki init` validiert nur Parse/Form (`opencode-config.ts:1012-1017`), `migrate` ist V1-Übersetzung.
